= The Big Picture

The UserManagement service is a business logic layer.
It sits between callers and a Data Access Layer (DAL), adding validation, hooks, and OTEL tracing to every operation.
It does not store data — it processes requests and forwards them.

Understanding this positioning is the key to understanding every architectural decision that follows.

== The Postal Service Analogy

Think of the system as a postal network.

NATS subjects are street addresses.
`motadata.user.create` is as specific as "123 Main Street."
Any message sent to that address lands in exactly one mailbox — the User entity handler's HandleCreate method.

The handler is the mailbox.
It receives the letter (incoming NATS message), checks it for completeness (validation), stamps it with business context (OTEL span attributes, hook results), and re-routes it to the warehouse address (the DAL subject `motadata.user.db.create`).

The DAL is the warehouse.
It stores and retrieves the actual goods.
The UserManagement service is the post office — it does not store anything, it processes and routes.

In this analogy, `demo.sh`'s mock DAL responders are a warehouse simulator: they accept any delivery and reply "received" without actually storing anything.
This lets the entire postal network — addressing, routing, validation, hooks — be tested without a real warehouse.

== The Two Flows

There are two distinct flows to understand: the _generation flow_ (how the code comes to exist) and the _runtime flow_ (what happens when a message arrives).

=== Generation Flow

....
MPS DSL (UserManagmentMps/)
  │
  │  TextGen templates run in MPS
  │
  ▼
source_gen/*.go  (MPS output)
  │
  │  sync.sh
  │    1. Copy .go/.sql to src/
  │    2. merge_hooks.py (extract hook stubs, preserve implementations)
  │    3. Extract project name from main.go first-line comment
  │    4. rsync SDK from ~/projects/nextgen/gosdk/
  │    5. Patch SDK module path (motadatagosdk → dev.azure.com/...)
  │    6. Fix SDK internal imports
  │    7. Kill processes on ports 4229/8222
  │    8. docker compose build && up
  │
  ▼
Running Docker container (NATS microservice)
....

The DSL is the single source of truth.
Every file in `src/` except `userDefinedHooks.go` is generated — it will be overwritten the next time MPS regenerates and `sync.sh` runs.
The only file safe to edit by hand is `userDefinedHooks.go`.

=== Runtime Flow

....
1. Client publishes: nats req motadata.user.create '{"username":"alice","email":"alice@co.com",...}'

2. main.go routes to User handler's HandleCreate method

3. HandleCreate:
   a. Start OTEL span "user.create"
   b. Unmarshal body → UserCreatedEvent
   c. Pre-hooks (sorted by priority):
        preCreateD (sync) → validate or abort
        preCreateM (async) → fire notification, continue
   d. Validate required fields (returns error if missing)
   e. Set span attributes (user.username, user.email, ...)
   f. NATS request → motadata.user.db.create (30s timeout)
   g. Post-hooks:
        postCreateNotifyAdmin (async) → fire admin alert
   h. Reply to original request with DAL response

4. DAL processes motadata.user.db.create and replies

5. Client receives response
....

[NOTE]
====
*Design rationale:* The subject split — `motadata.user.create` for incoming, `motadata.user.db.create` for DAL — is not accidental.
It means the UserManagement service can be inserted between any caller and any DAL without callers or the DAL needing to change their subject patterns.
The business layer is a middleware that speaks both languages.
====

== Component Responsibilities

[cols="1,3", options="header"]
|===
| Component | Responsibility

| MPS DSL (`UserManagmentMps/`)
| Single source of truth. Defines entities, fields, operations, relations, hooks, and the NatsServer configuration.

| TextGen templates
| Encode the handler recipe. Produce `user.go`, `roles.go`, `permissions.go`, `main.go`, and `sqlPrem_init_sql.sql` from DSL declarations.

| `merge_hooks.py`
| Extracts hook stubs from generated entity files, merges them into `userDefinedHooks.go`, and detects signature changes. Preserves user implementations across regeneration.

| `sync.sh`
| Orchestrates the full pipeline: copy from MPS, run merge, vendor+patch SDK, kill old containers, rebuild and restart.

| `userDefinedHooks.go`
| The only file safe to edit. Contains all business logic as hook implementations. Preserved across regeneration.

| Docker Compose
| Runs NATS (port 4229 external, 4222 internal) + the app container. The app connects to NATS at `nats://nats:4222` on the internal network.

| `demo.sh`
| 21 end-to-end tests. Spawns mock DAL responders, sends `nats req` messages, verifies responses.
|===

== The Subject Hierarchy

Every NATS subject in the system follows two patterns:

*Incoming (business layer):*
`motadata.{entity}.{operation}`

Examples: `motadata.user.create`, `motadata.roles.list`, `motadata.user.roles.assign`

*Outgoing (DAL):*
`motadata.{entity}.db.{operation}`

Examples: `motadata.user.db.create`, `motadata.roles.db.list`

For relations, the pattern extends: `motadata.{from}.{to}.db.{operation}`

This hierarchy is not configured anywhere — it is _generated_ by TextGen from the entity and relation names in the DSL.
Change an entity name in MPS and the subject strings change everywhere automatically.

== The NATS Micro Bridge

`main.go` uses the `nats.go/micro` package to expose the service over NATS's microservice protocol.
This gives the service:

* Automatic service discovery via `$SRV.INFO`
* Structured endpoint registration per operation
* A standard way to inspect what subjects the service handles

The service name comes from the first-line comment in the generated `main.go`:

[source,go]
----
// MotaDSLUM
package main
----

`sync.sh` extracts this comment with `head -1 src/main.go | sed 's|^// *||'` and passes it as a Docker build argument.
Single source of truth: the DSL's `NatsServer` concept generates the comment, and everything downstream (Dockerfile, container name) derives from it.

[NOTE]
====
*Design rationale:* Using a first-line comment as the service name source is pragmatic, not elegant.
A config file would be cleaner, but the comment is _generated automatically_ from the DSL's `NatsServer` concept — no manual configuration required.
The generator writes it; the pipeline reads it.
====

== What the System Does Not Do

Understanding system boundaries prevents surprises:

* *No persistence.* The UserManagement service does not connect to a database. All reads and writes go through the DAL.
* *No authentication.* Auth is handled upstream. The service assumes messages arrive from trusted callers.
* *No retry logic.* NATS request-reply uses a 30-second timeout. If the DAL does not respond, the call fails. No retry.
* *No schema migrations.* The generated `sqlPrem_init_sql.sql` creates the initial schema. Migrations are out of scope.

[WARNING]
====
*Watch for:*

* Editing files in `src/` that are not `userDefinedHooks.go`. They will be overwritten on the next `sync.sh` run.
* Hardcoded subject strings in hook implementations. If the entity name changes, generated subjects change but hardcoded strings in hooks do not.
* Missing mock DAL responders in test scripts. If `demo.sh` does not spawn a responder for a subject, tests for that entity will time out rather than fail with a clear error.
====
